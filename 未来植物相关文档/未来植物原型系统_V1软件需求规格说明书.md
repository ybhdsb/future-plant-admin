## 1. 文档说明

### 1.1 编写目的

本文档用于在 V1 开发启动前，把「要做成什么、做到什么程度、接口长什么样、和现有平台如何共存、谁在什么时候交付什么」一次说清楚，作为后续：

- 数据库表设计与迁移脚本编写
- MQTT / HTTP API 契约冻结
- 前后端分工与联调
- 国庆提前施工（目标：**2026-10-08 前完成关键路径工作**）
- V1 验收对照清单

的统一依据。

### 1.2 范围边界

**本文档覆盖（In Scope）**

- V1 最小可运行原型中的**控制系统软件**需求（采集、存储、查看、手动控制、导出）
- 与边缘控制器 / 传感器网关之间的**数据与指令接口定义**
- 在现有 Spring Boot + Layui 管理平台上的**模块接入方式**
- 刘振豪负责的前端相关任务细化与 10/08 前交付目标
- V2 仅做「接口预留」说明，不展开完整实现需求

**本文档不覆盖（Out of Scope）**

- 铝合金框架、水路、灯架等机械详细设计
- 供电配电图纸、RS485 寄存器位级协议细节（由电气交付《地址表/寄存器清单》，软件按契约消费）
- 科研级光谱分析、自动遮光闭环、自动水肥策略、能耗分析等 V2 能力的完整功能规格
- 联邦学习、猪场设备能力本体等与本原型无直接关系的既有业务改造（仅规定「不互相污染」）

## 2. 项目背景与目标

### 2.1 业务背景

原型系统采用铝合金型材独立框架，围绕玉米水培与未来植物光环境研究，按「先形成可运行原型、再逐步完善」建设。科研功能归并为四类：

1. 光环境与光调控（核心）
2. 多模态感知
3. 数据分析与可视化
4. 控制执行

V1 不以一次做全为目标，而是在约 6 周内打通：**结构 + 基础水培 + LED 光环境 + 风机/泵等执行 + 控制系统 + 可视化**，形成可连续运行、可展示、可扩展的第一版。

### 2.2 V1 产品目标（软件视角）

1. **能采**：温湿度、pH、EC 等已接入传感器数据可持续上报并入库（V1 传感器集合以电气实际接入为准，软件接口按统一模型预留扩展字段）。
2. **能控**：网页可手动控制 8 通道 LED、水泵、氧泵、通用开关、云台（及相机触发采集）。
3. **能看**：Dashboard 实时状态、设备在线、关键测点数值；历史曲线与图片记录可查。
4. **能导**：按时间/测点筛选并导出 CSV/Excel。
5. **能稳**：断连可感知、关键异常有日志、连续运行不丢核心链路。
6. **不乱**：与现有「设备管理 / 联邦学习 / 机器人」业务分区清晰，菜单与路由独立。

### 2.3 成功标准（V1 验收对应）

对应任务 **A01（2026-10-31）**，软件侧必须同时满足：

| 编号 | 验收项 | 通过标准 |
|------|--------|----------|
| AC-01 | 采集闭环 | 至少 1 类环境测点连续入库 ≥ 连续运行测试时长，前端可看到最新值 |
| AC-02 | 控制闭环 | LED 单通道亮度、水泵/氧泵启停可在网页触发并在现场生效；有指令回执或状态回读 |
| AC-03 | 存储闭环 | 遥测、控制日志、运行日志可查询 |
| AC-04 | 可视化闭环 | Dashboard + 历史曲线 +（若相机可用）图片记录可打开 |
| AC-05 | 导出闭环 | 选定时间窗导出文件可被 Excel 打开且字段含义正确 |
| AC-06 | 集成不破坏 | 原有设备列表、心跳、联邦学习页面功能无明显回归 |

### 2.4 建设原则（对软件的约束）

- **最小可运行优先**：先 Mock 通页面，再换真数据；先手动控制，后自动化策略（自动化属 V2）。
- **接口先行**：10/08 前必须冻结 MQTT/HTTP 字段与 topic 命名，电气与软件并行。
- **分阶段迭代**：V1 表结构与 API 必须能容纳 V2 传感器/执行器扩展，避免推倒重来。
- **复用现有平台，不污染现有业务**：未来植物作为独立业务域接入。

## 4. 系统总体设计（软件视角）

### 4.1 逻辑架构

```text
┌─────────────────────────────────────────────────────────────┐
│  Layui 管理端（未来植物独立菜单）                              │
│  Dashboard / 手动控制 / 历史曲线 / 数据管理(导出)              │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTP REST + WebSocket
┌───────────────────────────▼─────────────────────────────────┐
│  Spring Boot 平台（本仓库扩展 Plant 模块）                      │
│  PlantController / PlantCommandService / PlantTelemetryService│
│  复用：Devices 身份、MQTT 连接、登录鉴权、WebSocket 基础设施     │
└───────────────┬─────────────────────────────┬───────────────┘
                │ MQTT Command                │ MQTT Telemetry
                ▼                             ▼
┌───────────────────────────┐   ┌─────────────────────────────┐
│ 边缘控制器（RPi/Jetson）    │   │ 边缘控制器采集进程            │
│ 解析指令 → GPIO/继电器/LED │   │ RS485 轮询 → 上报遥测         │
└─────────────┬─────────────┘   └──────────────┬──────────────┘
              ▼                                ▼
        执行器设备                         传感器设备
   LED / 泵 / 氧泵 / 开关 / 云台      温湿度 / pH / EC / …(V2+)
```

### 4.2 与现有平台的集成原则（避免混乱）

| 原则 | 具体做法 |
|------|----------|
| 菜单隔离 | `index_view.ftl` 新增一级「未来植物」，下挂子页；不塞进「设备管理」大页 |
| 路由隔离 | 页面：`/plant/**`；API：`/plant/api/**`；WS：建议 `/ws/plant`（或复用 `/ws/device` 但消息带 `domain=plant`） |
| 代码隔离 | 新建 `controller/plant`、`service/plant`、`domain/plant`、`templates/plant_*.ftl` |
| 身份复用 | 现场控制器仍登记到 `devices`，`device_type` 建议 `plant_controller` / `raspberry`；业务数据不进 `devices` 宽表 |
| 传输复用 | 复用现有 MQTT Broker 与 `MqttService` 连接；**新增** plant 专用 topic，不占用 `jetson/train/*`、不改心跳语义 |
| 能力模块 | 暂不强制接入猪场 Capability Ontology；V1 只做在线/离线与控制回执 |

### 4.3 部署拓扑（V1）

- **平台**：现有 Spring Boot 服务（可本机或实验室服务器）。
- **Broker**：现有 MQTT（`application.yml` 中配置）。
- **边缘**：1 台控制器（树莓派/Jetson）负责采集与执行。
- **展示**：管理端浏览器；现场触摸屏可作为浏览器打开同一前端（V1 不单独做嵌入式 UI 框架）。

| UC-02 | 手动控制 LED 通道亮度 | 实验人员 | P0 |

| UC-10 | 自动策略（光周期/水肥） | — | P2（V2） |

### 5.3 典型流程：手动控制水泵

1. 用户打开「手动控制」页，确认控制器在线。
2. 点击「水泵开」，前端调用 `POST /plant/api/commands`。
3. 平台落库 `plant_command_log`，经 MQTT 下发 `plant/cmd/{deviceKey}`。
4. 边缘执行继电器动作，上报 `plant/ack/{deviceKey}` 或在下一包 telemetry 中回读状态。
5. 前端通过轮询或 WS 刷新按钮状态；失败则 Toast 错误原因。

### 5.4 典型流程：传感器数据入库展示

1. 边缘按配置周期（建议默认 5s，可配置）轮询 RS485。
2. 组装 Telemetry JSON，发布 `plant/telemetry/{deviceKey}`。
3. 平台订阅入库 `plant_sensor_reading`，并推送 WS。
4. Dashboard 更新数值；历史页可按 metric 查询。

### 6.2 前端功能详细需求

#### 6.2.1 页面骨架（S02）

**需求**

- 在后台增加「未来植物」菜单组，至少包含：
  1. 系统总览
  2. 设备控制
  3. 历史数据
  4. 数据管理（导出）
- 各页有统一页头：系统名称、控制器在线徽章、最后心跳时间、Mock/实机模式标识。
- 路由可深链；刷新不丢菜单高亮。

**非功能**

- 视觉风格与现有 Layui 后台一致，避免另起一套设计体系。
- 移动端仅需基本可用（演示以桌面为主）。

#### 6.2.2 Dashboard（S05）

**展示内容（P0）**

- 控制器在线/离线
- 关键测点卡片：空气温湿度、pH、EC（无数据时显示「未接入/Mock」）
- 执行器摘要：LED 总开关或通道摘要、水泵/氧泵状态
- 最近 N 条告警/异常（无则空状态）
- 数据新鲜度：各测点 `sampledAt` / `receivedAt`

**交互**

- 自动刷新：默认可选 WebSocket；降级为 3–5s 轮询。
- 提供「使用 Mock 数据」开关（仅开发/演示环境，或配置项）。

#### 6.2.3 手动控制（S06）

| 控件 | 行为 | 约束 |
|------|------|------|
| LED 通道 1–8 | 亮度 0–100（或 0–255，与电气冻结一致）；可单通道/全通道 | 下发前二次确认可选；离线禁用 |
| 水泵 | 开/关 | 显示目标状态与回读状态 |
| 氧泵 | 开/关 | 同上 |
| 通用开关 | 按配置动态渲染（relay_1…） | 名称来自设备配置 |
| 云台 | 上/下/左/右/停/复位 | 长按连续发令需防抖 |
| 相机 | 触发抓拍 | 返回任务 ID，稍后在历史看图 |

**安全（V1 最低）**

- 控制器离线时所有控制按钮禁用并提示原因。
- 每条指令写审计日志（操作者、时间、参数、结果）。
- V1 不做复杂互锁（干转保护等由电气硬件侧优先保障；软件侧预留 `safetyCode` 字段）。

#### 6.2.4 历史数据（S08）

- 按 `metric`、时间范围查询。
- 折线图（ECharts 或现有后台图表方案）。
- 图片/采集记录列表：缩略图、时间、关联 deviceKey。
- 空数据友好提示。

#### 6.2.5 数据管理与导出（S09）

- 筛选：时间范围、metric 多选、deviceKey（V1 可默认单控制器）。
- 导出 CSV、Excel。
- 导出文件命名：`plant_telemetry_YYYYMMDD_HHMMSS.csv`。
- 单次导出行数上限（建议可配置，默认 10 万行），超限提示缩小范围。

### 6.3 后端功能详细需求

#### 6.3.1 设备与数据模型（S01）

见第 7 章。

#### 6.3.2 采集接入（S03/S04）

- 平台订阅 Telemetry topic，校验、归一化、入库。
- 支持批量点位单包上报。
- 写入运行日志：连接、解析失败、重复心跳等。
- 边缘侧 RS485 抽象由软件 A 主责；平台只消费标准化 JSON。

#### 6.3.3 控制 API（S07）

- 统一命令入口，按 `commandType` 分发。
- 异步执行：HTTP 快速返回 `commandId`；结果靠 ACK / 状态回读。
- 支持幂等键 `clientRequestId`（可选），防止重复点击。

#### 6.3.4 联调与稳定性（S10/S11）

- 断连检测：沿用设备心跳超时或 plant 专用 lastTelemetry 超时。
- 命令超时：超时未 ACK 标记 `TIMEOUT`。
- 关键路径日志可检索。

## 8. 接口需求（重点：字段契约）

> 本章是刘振豪与后端/电气联调的**关键交付物**。V1 先冻结字段；寄存器映射表由电气另附。

### 8.1 Topic 规划

| 方向 | Topic | QoS | 说明 |
|------|-------|-----|------|
| 上行遥测 | `plant/telemetry/{deviceKey}` | 1 | 传感器与状态周期上报 |
| 下行指令 | `plant/cmd/{deviceKey}` | 1 | 平台 → 边缘 |
| 上行回执 | `plant/ack/{deviceKey}` | 1 | 指令执行结果 |
| （可选）事件 | `plant/event/{deviceKey}` | 1 | 告警/断连恢复等 |
| 既有心跳 | `jetson/device/status` | 1 | **继续用于在线身份**，不塞业务测点 |

**约束**

- 禁止把大块图片塞进 MQTT；图片走 HTTP 上传或边缘落盘后平台拉取。
- payload 一律 UTF-8 JSON。
- 时间一律 ISO-8601，建议带毫秒，统一用本地实验室时区或 UTC（**团队需二选一写进配置**，推荐 UTC 存储、前端转本地）。

### 8.2 上行 Telemetry（边缘 → 平台）

**你只需要约定「传感器给我什么字段」——推荐包结构如下。**

```json
{
  "schemaVersion": "1.0",
  "deviceKey": "plant-ctrl-01",
  "msgId": "t-20261008-000123",
  "sampledAt": "2026-10-08T12:00:00.123+08:00",
  "metrics": [
    {
      "metric": "air.temperature",
      "value": 26.4,
      "unit": "°C",
      "quality": "GOOD"
    },
    {
      "metric": "nutrient.ph",
      "value": 6.2,
      "unit": "",
      "quality": "GOOD"
    }
  ],
  "actuators": [
    {
      "actuatorId": "pump.water",
      "on": true
    },
    {
      "actuatorId": "led.ch1",
      "on": true,
      "brightness": 80
    }
  ],
  "extras": {
    "rs485BusOk": true,
    "pollMs": 5000
  }
}
```

**字段说明**

| 字段 | 必填 | 说明 |
|------|------|------|
| schemaVersion | 是 | 契约版本 |
| deviceKey | 是 | 与平台登记一致 |
| msgId | 是 | 边缘生成，便于去重 |
| sampledAt | 是 | 采样时刻 |
| metrics[].metric | 是 | 见 7.3 |
| metrics[].value | 是 | 数值；无读数可省略该点或 quality=BAD |
| metrics[].unit | 否 | 建议带上 |
| metrics[].quality | 否 | 默认 GOOD |
| actuators[] | 否 | 建议带，便于 UI 回读 |
| extras | 否 | 扩展，平台可原样入库 raw |

**平台处理要求**

1. 校验 `deviceKey` 存在且类型合法。
2. 逐条写入 `plant_sensor_reading`；更新 `plant_actuator_state`。
3. 推送 WS：`{ "type":"plant_telemetry", "deviceKey":"...", "summary":{...} }`。
4. 解析失败写 `plant_runtime_event`，不拖垮监听线程。

### 8.3 下行 Command（平台 → 边缘）

**你告诉边缘「要执行什么指令」——统一信封 + 分类型 payload。**

```json
{
  "schemaVersion": "1.0",
  "deviceKey": "plant-ctrl-01",
  "commandId": "c-10086",
  "clientRequestId": "ui-uuid-xxx",
  "commandType": "LED_SET",
  "issuedAt": "2026-10-08T12:01:00.000+08:00",
  "expiresAt": "2026-10-08T12:01:30.000+08:00",
  "payload": {
    "channels": [
      { "actuatorId": "led.ch1", "brightness": 80 },
      { "actuatorId": "led.ch2", "brightness": 60 }
    ]
  }
}
```

#### 8.3.1 commandType 枚举（V1）

| commandType | payload 要点 | 说明 |
|-------------|--------------|------|
| `LED_SET` | `channels[{actuatorId, brightness}]` | brightness 范围与电气冻结（建议 0–100） |
| `PUMP_SET` | `{ actuatorId, on }` | `pump.water` / `pump.oxygen` |
| `RELAY_SET` | `{ actuatorId, on }` | 通用继电器 |
| `GIMBAL_MOVE` | `{ action: UP/DOWN/LEFT/RIGHT/STOP/HOME, speed? }` | 点动或持续由边缘解释 |
| `CAMERA_CAPTURE` | `{ cameraId, reason? }` | 触发抓拍 |
| `CONFIG_RELOAD` | `{}` | 边缘重载本地配置（可选） |
| `PING` | `{}` | 连通性测试 |

#### 8.3.2 HTTP API（平台对前端）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/plant/api/dashboard` | 总览聚合 |
| GET | `/plant/api/device/{deviceKey}/state` | 最新测点+执行器状态 |
| GET | `/plant/api/metrics` | 历史查询：`metric,from,to,limit` |
| POST | `/plant/api/commands` | 下发指令（body 同信封，可无 schema 外层字段由服务端补） |
| GET | `/plant/api/commands/{commandId}` | 查询指令状态 |
| GET | `/plant/api/media` | 图片列表 |
| GET | `/plant/api/export/telemetry` | 导出（或 POST 任务式导出） |
| GET | `/plant/api/events` | 运行事件 |

**`POST /plant/api/commands` 请求示例**

```json
{
  "deviceKey": "plant-ctrl-01",
  "clientRequestId": "ui-uuid-xxx",
  "commandType": "PUMP_SET",
  "payload": {
    "actuatorId": "pump.water",
    "on": true
  }
}
```

**响应示例**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "commandId": "c-10086",
    "status": "SENT"
  }
}
```

### 8.4 上行 ACK（边缘 → 平台）

```json
{
  "schemaVersion": "1.0",
  "deviceKey": "plant-ctrl-01",
  "commandId": "c-10086",
  "status": "ACKED",
  "message": "ok",
  "finishedAt": "2026-10-08T12:01:01.200+08:00",
  "stateAfter": {
    "actuatorId": "pump.water",
    "on": true
  }
}
```

`status`：`ACKED` | `FAILED`（失败必须带 `message`）。

### 8.5 边缘配置文件（与 S03 对齐，供联调）

```json
{
  "deviceKey": "plant-ctrl-01",
  "pollIntervalMs": 5000,
  "serial": {
    "port": "/dev/ttyUSB0",
    "baudrate": 9600
  },
  "sensors": [
    { "metric": "air.temperature", "slaveId": 1, "parser": "modbus_th_v1" },
    { "metric": "nutrient.ph", "slaveId": 2, "parser": "modbus_ph_v1" }
  ],
  "actuators": [
    { "actuatorId": "pump.water", "type": "relay", "channel": 1 },
    { "actuatorId": "led.ch1", "type": "led_pwm", "channel": 1 }
  ]
}
```

> 具体 `parser` / 寄存器地址以电气《RS485 地址表》为准；软件配置只引用映射 ID。

### 8.6 HTTP 图片上传（建议）

`POST /plant/api/media/upload`  
`multipart`: `deviceKey`, `capturedAt`, `file`  
返回 mediaId，供历史页展示。

### 8.7 WebSocket 消息

```json
{
  "domain": "plant",
  "type": "telemetry" | "command_status" | "event" | "device_online",
  "deviceKey": "plant-ctrl-01",
  "payload": {}
}
```

### 8.8 错误码（建议）

| code | 含义 |
|------|------|
| 0 | 成功 |
| 40001 | 参数非法 |
| 40401 | deviceKey 不存在 |
| 40901 | 设备离线，拒绝下发 |
| 40902 | 指令冲突/过期 |
| 50001 | MQTT 发送失败 |
| 50002 | 内部错误 |
